# Reactive Resume · 求职套件

> 灵感来自开源项目 reactive-resume。它最珍贵的三件事被搬到这里：**隐私优先、数据自主、结构化单一数据源**。
> 你的简历和求职数据只存在本地 JSON 文件里，随时可以打包带走，不依赖任何云服务。

## 设计理念（先理解"为什么"，再动手）

1. **数据主权**。简历、JD、投递记录都是敏感信息，全部存本地文件，用户随时可查看、可备份、可迁移到任何工具。
2. **单一数据源**。简历内容只维护一份 `resume.json`；Markdown/HTML 渲染、ATS 检查、JD 匹配分析都从它生成。改内容只改一处，杜绝"改了这版忘了那版"。
3. **先结构，后排版**。先把事实和内容钉死，再谈模板和导出。排版永远是最后一步，且随时可以重来——所以不必在内容没写完时纠结字体。
4. **求职是一个系统，不是一张纸**。简历只是入口。投递、匹配分析、面试准备、复盘、Offer 比较共享同一套事实库（`career.json`），用得越久越准。

## 数据文件约定

默认存放在当前工作目录的 `reactive-resume/` 下（用户指定其他位置时从其愿）：

| 文件 | 内容 | 何时创建 |
|---|---|---|
| `reactive-resume/resume.json` | 简历单一数据源 | 创建/重建/定制简历时 |
| `reactive-resume/career.json` | 职业档案、投递跟踪、事实库、故事库、面试记录、Offer | 任何求职管理动作时 |
| `reactive-resume/outputs/` | 渲染出的 Markdown / HTML 成品 | 每次渲染 |

规则：

- 文件不存在时，先读对应的 `references/*-schema.md`，按 schema 建骨架再填充。**字段即契约，不要凭空发明字段**——`scripts/validate_resume.py` 按 schema 校验。
- 为某公司定制简历时，复制为 `resume-<公司名>.json` 再改，原版保留。
- 每次改动后跑一次校验，保持零错误。

## 工作流路由

先判断用户意图，进入对应工作流。意图不明时，直接问，别猜。

### A. 从零创建 / 重建简历

1. **访谈采集，不要一上来就写**。按这个顺序问：目标岗位 → 最近一段经历（公司/职位/时间/做了什么/结果如何）→ 逐段往前推 → 教育 → 技能证书 → 加分项。每轮问 2–4 个问题，不要一次甩一张巨表。
2. 用户答得笼统时，用 `references/writing-playbook.md` 的追问术挖数字（"当时团队多大？""提升了多少？""用什么方法做到的？"）。挖不到就如实留空，标"待补充"。
3. 写入 `resume.json` → `python3 scripts/validate_resume.py validate <文件>` → 修到零错误。
4. `render` 生成 Markdown/HTML → 按 `references/ats-guide.md` 过一遍 ATS 检查。
5. 交付时明确区分：哪些是用户提供的事实，哪些是你给出的改写建议，哪些留空待用户补充。

### B. 针对 JD 优化现有简历

1. **先做匹配分析（fit），再改内容**。把 JD 要求逐条拆成清单，每条标注 `具备 / 部分 / 缺失` 并附简历中的证据；没有证据的进"待确认"清单。**严禁编造证据**——这一条比改得好不好更重要。
2. 差距分两类处理：能补的（关键词、量化、措辞）给出改写前后对照；不能补的（缺经验、缺证书）诚实告知，建议用可迁移能力或学习计划弥补，而不是硬凑。
3. 改写后重新 validate + ATS 检查。
4. 用户要求定制版时，另存 `resume-<公司名>.json`。

### C. 求职信

- 结构：称呼 → 为什么是这家公司（引用具体事实：产品/业务/新闻，忌"久闻大名"式空话）→ 为什么是我（2–3 个与 JD 最强匹配的证据，优先引用事实库）→ 收尾与行动号召。
- 控制在一页以内；专业但不僵硬；与简历内容一致，**绝不引入简历里没有的经历**。

### D. 投递跟踪

- "投了 X" → 在 `career.json` 投递数组追加一条：公司/职位/日期/渠道/阶段=已投递/用了哪版简历。
- "有回复了 / 约面了" → 更新阶段、追加时间线、设置"下一步"（事项 + 截止日期）。
- "我投得怎么样了" → 输出看板：按阶段分组的表格 + 超期未跟进的提醒 + 本周待办。
- 阶段状态机：`已投递 → 筛选中 → 面试中 → offer / 已结束`。标记"已结束"时必须记录原因，方便复盘。

### E. 面试准备

针对某次面试生成 briefing（结构见 `references/career-schema.md`）：

1. 已知信息对齐：公司/岗位/面试官/轮次/形式。
2. 高频问题清单 5–8 个，优先覆盖该岗位 JD 匹配分析里的"部分/缺失"项——面试官大概率会问。
3. 每个问题关联故事库里的 STAR 故事；缺故事先访谈采集再入池。
4. 3 分钟开场白 + 3 个反问对方的问题 + 时间盒计划（例：60 分钟 = 20 分钟过故事 + 25 分钟模拟问答 + 15 分钟准备反问）。

### F. 面试复盘

1. 自评发挥（`很好 / 一般 / 没发挥好`）→ 记录哪个问题答得好、哪个砸了、为什么。
2. 把复盘中冒出来的新事实、新故事补进事实库/故事库——复盘的价值在下一场面试，不在自责。
3. 生成下周改进计划，每天不超过 3 项。

### G. Offer 比较

- 统一维度比较：月base/年终奖/股票/公积金比例/年假/每周到岗天数/通勤/成长空间/团队氛围，换算"年总收入 + 有效时薪"辅助决策。
- 结合 `career.json` 里的职业档案（优先级、薪资底线、到岗天数上限）给分析，但把决定权交给用户。

## 写作与 ATS 红线（细节在 references）

- 经历描述 = STAR + 数字：动作 → 对象 → 方法 → 量化结果。
- 写成就，不写职责：把"负责 X"改写成"完成了 X，带来 Y"。
- ATS 底线：单栏优先、标准字体、无表格无图标文字、日期格式统一为 `YYYY-MM`、联系方式纯文本、投递用 PDF 或 DOCX。
- 完整方法与清单见 `references/writing-playbook.md` 和 `references/ats-guide.md`。

## 交付前检查（每个任务收尾时逐项过）

- [ ] `resume.json` / `career.json` 通过 `validate_resume.py`，零错误
- [ ] 没有任何编造的事实、数字、公司信息；存疑处已标注
- [ ] ATS 检查清单已过（见 `references/ats-guide.md`）
- [ ] 需要用户补充/确认的内容已明确列出
- [ ] 原版文件未覆盖（定制版另存）

## 工具依赖

`scripts/validate_resume.py` 只用 Python 3 标准库，无需安装任何包。生成 Word/PDF 成品时，交给环境里的 `docx` / `pdf` 技能完成，本技能负责内容与结构。
