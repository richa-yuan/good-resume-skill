# 求职管理数据结构（career.json）

> 字段设计参考 reactive-resume 的 career schema（workspace tabs: fit → apply → prepare → practise → debrief → messages → saved），已中文化。求职管理的一切状态都在这一个文件里。

> 下文示例统一用「用户增长运营」角色演示，**技术研发 / 产品销售 / 职能管理 / 设计等任意行业字段完全一致，只换文字内容**。

## 顶层结构

```json
{
  "版本": "1.0",
  "职业档案": {},
  "投递": [],
  "事实库": [],
  "故事库": [],
  "面试准备": [],
  "复盘": [],
  "Offer": []
}
```

## 职业档案（求职前的自我定位）

```json
{
  "目标岗位": ["用户增长负责人", "增长总监"],
  "目标城市": ["杭州", "上海", "远程"],
  "优先级": "成长空间 > 团队质量 > 薪资 > 通勤",
  "薪资底线": { "金额": 35000, "货币": "CNY", "周期": "月" },
  "最多到岗天数": 3,
  "离职通知期周数": 4
}
```

- `优先级`：用用户自己的话记下来，Offer 比较和面试反问时都要参照。
- `薪资底线`：单位是 `月` 或 `年`，比较 Offer 前先统一口径。

## 投递数组（每个元素是一次投递）

```json
{
  "id": "app-1",
  "公司": "某大厂",
  "职位": "用户增长负责人",
  "渠道": "内推 / 官网 / 猎头",
  "阶段": "面试中",
  "投递日期": "2026-10-20",
  "JD原文": "（粘贴或摘要）",
  "JD链接": "",
  "匹配分析": {
    "概述": "整体匹配度较高，活动操盘与裂变拉新是亮点，缺少 B 端 / 商业化增长的直接证据",
    "要求": [
      { "文本": "5 年以上运营 / 增长经验", "来源": "JD", "状态": "具备", "证据": "6 年经验，见经历 exp-1" },
      { "文本": "大型 C 端用户增长经验", "来源": "推断", "状态": "部分", "证据": "有 C 端大促增长，但非 DAU 千万级长期操盘" }
    ],
    "待确认": ["是否接受纯管理岗", "团队是否偏 B 端增长"]
  },
  "简历版本": "resume.json / resume-某大厂.json",
  "时间线": [
    { "日期": "2026-10-20", "事件": "投递" },
    { "日期": "2026-10-24", "事件": "HR 约一面" }
  ],
  "下一步": { "事项": "准备一面（增长策略深挖 + 大促复盘）", "截止": "2026-10-30" },
  "备注": ""
}
```

**阶段状态机**：`已投递 → 筛选中 → 面试中 → offer / 已结束`。

- 标记 `已结束` 时在备注里写原因（挂了/主动撤/薪资不符），复盘时用。
- `匹配分析.要求[].状态` 三值：`具备`（有证据）/ `部分`（沾边但不够）/ `缺失`（没有）。**证据必须能在简历或事实库里找到，找不到就标缺失或进待确认，不许编。**
- `待确认`：需要问 HR/面试官的问题，面试前集中准备。

## 事实库（facts）——一切改写的弹药库

```json
{ "id": "fact-1", "文本": "主导双十一增长专项，GMV 同比 +58%", "分类": "成就", "来源": "简历 exp-1" }
```

- `分类`：`成就 / 经历 / 技能 / 偏好`。
- 每挖到一条可量化的事实就入库。JD 匹配分析、求职信、面试故事都从这里取料——这是"越用越准"的关键。

## 故事库（stories）——面试叙事的 STAR 池

```json
{
  "id": "story-1",
  "标题": "双十一增长攻坚",
  "情境": "去年双十一大促 GMV 不达预期，老板要求增长专项把 ROI 拉回 3 以上",
  "任务": "我负责增长专项，三周内给出方案并落地",
  "行动": "用数据看板 + AB 实验定位到拉新成本偏高和转化漏斗流失两大瓶颈，推动裂变玩法重构、落地页改版、投放渠道重分配",
  "结果": "大促 GMV 同比 +58%，活动 ROI 从 1.8 提升到 3.2，方案沉淀为团队增长规范",
  "反思": "先测量后优化；推动跨团队改造时，用数据说话比方案本身更重要",
  "标签": ["用户增长", "推动协作"]
}
```

面试准备的每个问题都尝试挂到故事库的某个故事上；讲不出来的故事 = 还没准备好的故事。

## 面试准备（briefings）

```json
{
  "id": "brief-1",
  "投递id": "app-1",
  "公司": "某大厂",
  "轮次": "一面（业务）",
  "日期": "2026-10-30",
  "问题清单": [
    { "问题": "介绍你操盘过的一次增长项目", "关联故事": "story-1", "来源": "JD 匹配分析·部分项" }
  ],
  "开场白": "3 分钟自我介绍草稿……",
  "反问问题": ["团队目前最大的增长挑战是什么？", "这个岗位未来半年的核心目标？"],
  "时间盒": [ { "分钟": 20, "事项": "过故事库 3 个核心故事" }, { "分钟": 25, "事项": "模拟问答" }, { "分钟": 15, "事项": "准备反问 + 查公司最新动态" } ]
}
```

## 复盘（debriefs）

```json
{
  "id": "debrief-1",
  "投递id": "app-1",
  "日期": "2026-10-30",
  "轮次": "一面",
  "自评": "一般",
  "答得好": ["增长项目复盘问题，用了 story-1，数据完整"],
  "答得差": ["被问 B 端商业化增长细节答不上来——只做过 C 端，没碰过 B 端"],
  "新事实": ["补一条：商业化增长只有学习经验，不要写成主导"],
  "改进计划": [ { "天": "mon", "分钟": 30, "事项": "补 B 端商业化增长方法论笔记" } ],
  "下一步": "等二面通知；若进二面重点准备场景设计题"
}
```

复盘规则：`新事实` 必须同步进事实库；`改进计划` 每天不超过 3 项。

## Offer 比较

```json
{
  "id": "offer-1",
  "投递id": "app-1",
  "公司": "某大厂",
  "版本": "书面",
  "月base": 42000,
  "年终奖月数": 4,
  "股票": "RSU 40万/4年",
  "公积金比例": "12%",
  "年假": "15 天",
  "每周到岗天数": 3,
  "通勤单程分钟": 45,
  "成长与团队": "增长中台组，方向匹配",
  "回复截止": "2026-11-15"
}
```

比较时统一换算：`年总收入 ≈ 月base × (12 + 年终月数)`，股票按 4 年摊；再结合职业档案的优先级给分析。**分析给足，决定权留给用户。**
